## 算定について（既存の実装で採っているもの）

| 決定 | 理由 |
|---|---|
| 外壁後退と斜線による後退は、足さずに大きいほうを適用する | どちらも境界線からの離れで、大きいほうだけが効くため |
| 天空率の計画建築物は全階同一平面の箱。階数は容積率を使い切る最小 | 上階の後退をなくすのが天空率を使う狙いのため |
| 適合建築物は境界線ごとに作り（敷地区分方式）、高さは計画建築物の最高高さで頭打ちにする | 隣地について頭打ちの要否が条文から一義に読めず、厳しい側を既定にした。頭打ちなしなら余裕は広がるので、「通る」と出れば読み方によらず通る |
| 北側斜線は真北方向に敷地を収縮させる形で解く | 辺ごとの帯では表せないため |
| 複数案は斜線を守った延床の順に並べ、外壁後退ごとの最良案を末尾に足す | 天空率で開ける案が下位に埋もれないようにするため |
| 収まらない階は切り捨てる（板は絞らない） | 既知の挙動。容積率を使い切る方針は未決定の論点として残す |

## システムの構成について（2026-09-15 の検討）

| 決定 | 理由 |
|---|---|
| 用地探索から総合図作成者への受け渡しまでを1つのシステムとして作る。段の間には人が決める関門を置く | 全自動にすると人が決めるべき判断を機械が埋めることになるため |
| ~~総合図そのものは作らない。通り芯・階レベル・コア・PS/EPS を基準データとして渡すまで~~ **→ 0004 で変更（確度つきで作る）** | 総合図に描く梁・設備・機器は、構造設計・設備設計・製品選定の結果がないと決まらない。推測で埋めると、精密に見えて中身のない図になる |
| 仮の天井・設備検討図は第3段の後に検討する | 階高チェックとして価値はあるが急がない |
| 通り芯とレベルは、描くだけでなくデータとして持つ | 後の受け渡しと天井・設備検討の土台にするため |
| ~~設備機器・天井割のデータ構造は今は作らない~~ **→ 0004 で変更（M10 以降で作る）** | 根拠のない既定値を持つことになるため |
| 既存コードは作り替えず、包んで移行する（M00 → M02） | 検算済みの算定を失わず、従来結果との一致を数値で示すため |
| 案の保存は SQLite から始める | 社内利用の間は十分。公開の段で移す |
| 会話は MCP サーバーを早く入れ（M04）、Web チャットは後（M09） | 画面を作らずにツールの粒度を試せる。Web チャットは同じ定義を使い回せる |
