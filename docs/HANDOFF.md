## 1. これは何か

オフィス・テナントビルの企画段階で、敷地条件と法規条件から**建築可能ボリューム**を算定し、断面図・配置図・各階平面図・面積表を **DXF 1枚**と Web 画面に出すツール。
「敷地を指定するだけで法規条件を取得し、複数案を自動生成する」ところまで来ている。

**企画検討用の試算であり、確認申請には使えない。** 出力の注記・画面・README すべてにその旨がある。

## 4. 守ってきたルール（新プロジェクトでも継続すること）

1. **法規定数は `constants.py` に集約し、条文番号をコメントで付ける。** 直書きしない。
2. **法規の値で迷ったら推測しない。** 調べて一般的な値を採るか、読み切れなければ「厳しい側」を既定にして理由を書く（例: 隣地の適合建築物の高さ、§5）。
3. **手計算の検算を先に書き、実装をそれに合わせる。** 実装の出力を期待値に写さない（`tests/test_solver.py` の手計算ケース）。
4. **土台を入れ替えるときは従来結果との一致を数値で示す。** 多角形化のときは矩形の DXF 全図形が byte 一致することを確認した。
5. **性質が成り立たなくなったら、テストを黙って書き換えない。** 報告して合意してから直す（「道路幅員を広げると階数が減らない」は成り立たなかった）。
6. **未考慮事項は出力に印字する。** `VolumeResult.notes` → 画面と DXF の両方に出る。
7. **算定の重い最適化は「結果が変わらない」ことを示してから入れる**（格子判定のベクトル化、適合建築物の層の畳み込み）。
8. テストが通らない状態で次へ進まない。

## 5. 判断した設計上の選択と理由

- **shapely を入れた。** 当初は「幾何ライブラリ不使用」だったが、任意形状対応で必要になった。矩形が従来と厳密一致することをテストで担保。numpy も（天空率・格子判定）。
- **外壁後退と斜線は max。** 当初仕様は足し算。どちらも「境界線からの離れ」なので大きいほうだけが効く。変更で道路12mサンプルは 3,473→3,556㎡、最大の削減要因が道路斜線→建蔽率に入れ替わった（僅差）。
- **天空率の計画建築物＝全階同一平面の箱。** 上階の後退をなくすのが天空率の狙いなので。階数は容積率を使い切る最小。通らなければ外壁後退を0.5m刻みで広げて通る案を探す。
- **適合建築物は境界線ごと（敷地区分方式）、高さは計画建築物の最高高さで頭打ち。** 道路は令135条の6の建て付け。隣地は条文から一義に読めなかったので厳しい側を既定にし、頭打ちなしなら余裕が必ず広がることをテストで担保（`NEIGHBOR_ENVELOPE_CAPPED`）。
- **算定線は「斜線面がどこから見ても仰角一定に見える線」。** 道路＝反対側の境界線、隣地＝立ち上がり÷勾配だけ外側（16m/12.4m）。この性質があるので適合建築物の層厚は答えに効かない（テスト済み）。
- **北側斜線は真北向きの線分で敷地を収縮（erosion）。** 辺ごとの帯では表せない。凸なら「敷地∩南へずらした敷地」で厳密、凹は中間点も課す。
- **solve() は板を絞らず、収まらない階を切り捨てる。** そのため防火地域で耐火にすると建築面積は増えるのに延床が減ることがある（テストで明記）。板を絞って容積を使い切るのは `skyfactor.planned_slabs` の役目。
- **複数案の表は延床順。** 天空率で開ける案（外壁後退大）は下に来るので、後退ごとの最良案を末尾に足している。
- **DXF は mm 実寸。** ezdxf は保存時に `$EXTMIN` 等をレイアウトの値で上書きするので、`msp.dxf.extmin` 側に書く。

## 6. 未対応・既知の限界

| 項目 | 状態 | 影響 |
|---|---|---|
| **日影規制**（法56条の2・別表第四） | 未実装 | 住居系で致命的。「日影規制の対象区域」を立てると北側斜線が外れるだけで**安全側ではない**（注記あり） |
| 北側斜線の天空率（令135条の8・11） | 未対応 | 北側斜線がかかる案件では天空率「通る」が不完全（`north_slant_unchecked` で明示） |
| 法56条4項 後退距離の緩和、令132条 2以上の前面道路、法52条9項 特定道路 | 未考慮 | 実際より小さく出る（安全側） |
| 容積率不算入（EV・共用部・駐車場） | 未考慮 | 床面積＝容積対象。実際より厳しい |
| 高さの算入除外（令2条1項6号ロ 屋上部分） | 未考慮 | |
| 高低差・高低差区分区域 | 未対応 | 敷地は平坦前提 |
| 高度地区・地区計画・道路種別 | 取得不可 | 手入力。公開 API にない |
| 天空率の市販ソフト（ADS 等）との照合 | 未実施 | 定義に対する独立検証のみ。確定判定には使えない |
| 用途地域自動取得 | 要 API キー | なければ手入力 |

## 7. 開発環境の注意

- venv: `volume_check/.venv`（Python 3.14、`uv venv` + `uv pip install`）。実行は `.venv/Scripts/python.exe`
- 実行時依存: `requirements.txt`（ezdxf / shapely / numpy / fastapi / uvicorn / httpx）。pytest・matplotlib は含めない
- `.claude/launch.json` に開発サーバー定義（port 8790）。**uvicorn の --reload が効かない環境なので、コード変更後はサーバーを再起動する**
- Bash の heredoc に日本語・バックスラッシュを含む Python を渡すと壊れる。**パッチはファイルに書いてから実行する**
- DXF の改行は CRLF
- Railway: Root Directory 未設定で正解（リポジトリのルートが `volume_check/` の中身）。`PORT` は Railway が 8080 を渡す

## 8. これからの道筋（合意済みの方向）

「総合図へ進む」前提で、箱に骨格を入れていく。**① コア計画から着手**で合意。

第1段（箱に骨格）
1. **コア計画** — コア位置候補（センター／サイド／2コア）、EV台数（交通計算の簡易版）、階段2か所（令121条）、31m超の非常用EV（法34条2項）→ 根拠のある有効率と**基準階平面図**
2. 避難・防火チェック — 歩行距離（令120条）、面積区画（令112条）、非常用進入口（令126条の6）を警告で
3. 構造グリッド — スパン割、必要階高の逆算

第2段（事業性）
4. 駐車・駐輪・荷さばき（自治体条例は入力）、容積不算入
5. 事業収支 — 概算工事費・賃料・NOI・利回り。**複数案の並びを延床順から利回り順へ**

第3段（図面セット）
6. 配置図・各階平面図・断面図・立面図・面積表の DXF セット
7. 総合図への受け渡し — 通り芯・階レベル・コア・PS/EPS を構造・設備が引き取れる形（レイヤ規約、将来 IFC）

並行: 日影規制（第1段と同時期に）

対話式（設計者が自然言語で条件を伝える形）は **MCP サーバー → Web のチャット欄** の順。LLM は翻訳と説明だけ、数値はすべて solver から。各機能は「コアを東に寄せて」と言える単位で切る。

## 9. 直近の使い方の勘所

- 商業・近商・工業系: そのまま使える
- 住居系: 北側斜線まで入っているが日影規制がないので、中高層住専では注意
- 地図は「敷地の頂点をなぞる」→ 辺の中点の丸で道路/隣地を切替 → 幅員は道路辺に共通
- 天空率で×が出たら「通る案」（外壁後退を広げた案）が提示される。隣地側だけ落ちた案は実際には通る可能性がある（厳しい側で判定しているため）
