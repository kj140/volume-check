# システム全体設計（提案）— 敷地から総合図まで

**状態：** 決定（2026-09-27 承認、`docs/decisions/0004`）
**日付：** 2026-09-26
**関係：** `docs/architecture.md` を延長する。範囲と層の要点は `architecture.md` に取り込み済み。総合図の段（建物モデル・配置・調整・取り込み）の詳細はこの文書を正とする。

---

## 0. この文書の要点

1. 敷地の指定から総合図の出力までを、**段をつないだ1本の流れ**として作る。段と段の間には人が決める関門を置く。
2. 総合図は「図」ではなく、**建物モデル**（部材の集まり）の見え方の一つとして作る。
3. 建物モデルの部材には、すべて**確度**（仮定・計画・設計・確定）を持たせ、図面でも描き分ける。企画段階の仮定だらけの総合図も、仮定だと一目で分かる形で出す。
4. 部材を**置く**のも、ぶつかりを**調べる**のも、決まった計算（solver）が行う。LLM は指示の翻訳、直し方の候補出し、結果の説明を担い、位置や数値を決めない。
5. **法規**（直さなければ建たない）と**設計標準**（設計者の判断で外せる）を別の表に持ち、指摘の重さを分ける。
6. 構造・設備の設計者から届く図面（DXF・IFC）を取り込み、仮定の部材を置き換えていく。**最後は取り込んだ図面を調整する本来の総合図**になる。

決定 `0001` の「総合図そのものは作らない」は、その理由（根拠のない部材が精密に見えてしまう）を、3. の確度で解消したうえで改める提案である（`docs/decisions/0004`）。

## 1. 目的と範囲

### 1.1 目的

オフィス・テナントビルについて、**敷地を指定すると、法規条件の取得 → 建てられるボリュームと複数案 → 骨格（コア・柱・階高）→ 事業性 → 各分野の部材を載せた建物モデル → 干渉の調整 → 総合図**までを、同じデータの上で進められるようにする。

使う人は設計者。ツールは「設計者が決める前に、決めるための数字と図をそろえる」ことと、「各分野の図面を重ねて、ぶつかる所を見つける」ことを担う。

### 1.2 範囲（改定案）

| 範囲に入る | 範囲に入らない |
|---|---|
| 用地候補の評価、法規条件、ボリューム、複数案 | 確認申請図書 |
| 概算、事業収支（幅で出す） | 見積書 |
| コア計画、柱グリッド、階高 | **構造計算**、**設備設計**（負荷計算・機器選定） |
| 建物モデル（仮定の部材を含む。確度つき） | 仮定の部材を「設計済み」として出すこと |
| 天井割・設備機器の**仮配置**（ルールによる） | 意匠デザイン |
| 他社図面の取り込み、干渉・離隔・範囲漏れの調整 | 施工図（製作図） |
| **総合図**（天井伏・床・壁・断面詳細）、DXF・PDF・IFC | 行政協議・消防協議の代行 |

**構造計算と設備設計はしない**点は変えない。建物モデルに載る梁の寸法や設備の配置は、それらの設計の**代わり**ではなく、設計が届くまでの**仮置き**であり、確度で区別する。

## 2. 全体の流れ

```
 ① 敷地        ② ボリューム     ③ 骨格           ④ 事業性
 地図でなぞる → 法規・斜線・  → コア・EV・階段 → 概算・収支
 法規条件取得   天空率・複数案   柱グリッド・階高   案の選定
      ◆関門A          ◆関門B           ◆関門C          ◆関門D
                                                        │
 ┌──────────────────────────────────────────────────────┘
 ▼
 ⑤ 建物モデル                    ⑥ 調整                 ⑦ 総合図
 構造の仮定（梁・柱）        →  干渉・離隔・範囲漏れ →  天井伏・床・壁・断面
 天井割・設備の仮配置           指摘一覧・直し方の候補    DXF・PDF・IFC
      ▲                              ◆関門E                 ◆関門F
      │
 他社図面の取り込み（構造図・設備図 → 仮定を置き換える）
```

| 関門 | 人が決めること | 機械が出す判断材料 |
|---|---|---|
| A | 敷地の形・道路・法規条件が正しいか | 取得した値と出所、取れなかった項目 |
| B | 検討を進める案 | 複数案の比較（延床・高さ・天空率・削減要因） |
| C | コア方式・スパン・階高 | 有効率、EV 台数、法規チェック（階段・非常用 EV） |
| D | 進める案 | 概算・収支・利回りの比較 |
| E | 指摘ごとの対応（直す・許容する・分野に差し戻す） | 指摘一覧、直し方の候補（規定を満たすものだけ） |
| F | 出図してよいか | 未解決の指摘、確度0の部材の割合、未考慮事項 |

関門で人が決めた内容は、案の**履歴**として残す（「誰が・いつ・何を根拠に」）。

## 3. 確度（すべての部材が持つ）

| 確度 | 名前 | 意味 | 誰が作るか | 図での表し方（案） |
|---|---|---|---|---|
| 0 | 仮定 | 設計標準から仮に置いた | 配置エンジン | 薄い破線、「仮」の記号 |
| 1 | 計画 | 設計者が決めた・動かした | 設計者（画面・会話） | 細い実線 |
| 2 | 設計 | 各分野の設計図から取り込んだ | 取り込み | 実線 |
| 3 | 確定 | 製品・品番まで決まった | 取り込み・設計者 | 太い実線、品番を表記 |

約束：

- 確度は**上がる方向にだけ**置き換わる。確度2の梁を、確度0の仮定で上書きしない。
- 図面の凡例に確度の描き分けを必ず載せ、紙面の注記に「確度0の部材の数と割合」を出す。
- **確度0の部材どうしの干渉**は「仮定どうしのぶつかり」として軽い指摘にし、確度2以上が絡む干渉と区別する。

## 4. 層の構成

```
web/         画面（地図・チャット・図面ビュー・指摘一覧・取り込み画面）
tools/       LLM 用ツール（MCP と Web チャットで共用）
api/         案・段の実行・取り込み・指摘・出図
──────────────────────────────────────────────────
solver/      算定（入出力を持たない純粋な計算）
  law/         法規定数（建築基準法・消防法など。条文番号つき）
  volume/      ボリューム（既存を包む）
  core/        コア計画
  grid/        柱グリッド・階高
  estimate/    概算・収支
  structure/   構造の仮定（梁せい・柱寸法の仮置き。構造計算ではない）
  place/       配置エンジン（天井割・設備機器の仮配置）
  coord/       調整エンジン（干渉・離隔・範囲漏れ）
standards/   設計標準（法規ではない。会社・案件ごとに差し替えられる表）
model/       データモデル
  building/    建物モデル（部材・確度・分野・階）
import/      他社図面の取り込み（DXF・IFC → 建物モデル）
drawing/     図面モデル → DXF / PDF / IFC
store/       保存（SQLite から始める）
data/        外部データの取得（出典・取得日つき）
```

依存の向き（現行の約束の延長）：

- `solver/` が import してよいのは `model/` と `standards/`（読むだけ）。
- `import/` は外部ファイルを読んで `model/building` の部材を作るだけ。算定しない。
- `drawing/` は建物モデルと段の結果を読むだけ。
- `tools/` は `api/` を呼ぶだけ。
- 依存の向きはテストで検査する。

## 5. 建物モデル

### 5.1 部材

```python
class Element:
    id: str
    kind: str                 # 下の「部材の種類」から
    discipline: Literal["arch", "struct", "elec", "mech", "plumb", "fire"]
    level: str                # "3F" など。階をまたぐ部材は from/to を持つ
    geometry: Geometry        # 平面形（点・線・多角形）＋ 高さ方向の範囲 [z_min, z_max] mm
    clearance: Clearance|None # 周りに要る空き（点検・保守・離隔）
    confidence: Literal[0, 1, 2, 3]
    origin: Origin            # 誰が・何から作ったか（ルール ID、取り込み元ファイルとレイヤ、設計者）
    attrs: dict               # 種類ごとの属性（品番、容量、器具の大きさなど）
```

部材の種類（最初に扱うもの）：

| 分野 | 種類 |
|---|---|
| 建築 | 外壁、コア壁、天井面、天井グリッド、点検口、OAフロア |
| 構造 | 柱、大梁、小梁、スラブ、梁貫通孔 |
| 電気 | 照明器具、非常照明、コンセント、スピーカー |
| 空調 | 吹出口、吸込口、ダクト（幹線）、機器 |
| 衛生 | 配管（幹線）、PS 内の立て管 |
| 防災 | 感知器、スプリンクラーヘッド、排煙口 |

### 5.2 案との関係

- 建物モデルは**案ごと・段の結果として**持つ（`StageResult.stage = "building"`）。
- 案は書き換えない（現行の約束）。設計者が部材を動かしたら、「親案＋差分」で子案を作る。
- 取り込みも同じ扱いにする。「この案に構造図 rev.3 を取り込んだ」ものが子案になる。どの図面の何版を入れた案かを必ず追える。

### 5.3 上流が変わったとき

| 部材の出どころ | 上流（ボリューム・コア・グリッド・階高）が変わったとき |
|---|---|
| 確度0（配置エンジン） | 作り直す |
| 確度1（設計者が動かした） | 残す。新しい条件で調べ直し、合わなくなったら指摘に出す |
| 確度2・3（取り込み） | 残す。調べ直して指摘に出す。**勝手に動かさない** |

## 6. 配置エンジン（solver/place）

ルール表に従って、確度0の部材を置く計算。

1. **天井割**：天井面を、システム天井のモジュール（`standards/`）で割り付ける。コア・柱・梁の位置に合わせて端部の調整を記録する。
2. **照明**：天井グリッドに沿って、目標照度（`standards/`）を満たす間隔で置く。照度計算はしない場合、間隔は標準値からの仮置きであることを記録する。
3. **感知器・スプリンクラー**：受け持ち範囲の規定（`solver/law/`、消防法）を満たすよう置く。**範囲の全点が受け持ちに入る**ことを配置の条件にする。
4. **吹出口・吸込口**：モジュールに沿って標準の密度で置く。
5. **点検口**：機器の近くに、標準の間隔で置く。

約束：

- 置いた部材はすべて `origin.rule_id` を持ち、どのルールで置いたかを追える。
- ルールで置けなかった場所（梁や柱と重なって置けない、範囲を満たせない）は、黙って飛ばさず**指摘として出す**。
- 設計者が確度1で置いた部材がある場所には、仮定の部材を重ねて置かない。

---

## 7. 調整エンジン（solver/coord）

建物モデルを調べて**指摘**を出す。直さない（直すのは人か、提案を人が採用したとき）。

### 7.1 調べること

| 種類 | 内容 | 例 |
|---|---|---|
| ぶつかり | 部材どうしの立体が重なる | 照明の埋め込みと大梁、ダクトと梁 |
| 離隔不足 | 必要な空き（`clearance`）に他の部材が入る | 感知器と吹出口、点検口の前 |
| 範囲漏れ | 受け持ち範囲に入らない場所がある | 感知器・スプリンクラー・非常照明 |
| 納まり | 天井の懐に入らない | ダクト＋梁せい＞天井高〜床下の寸法 |
| 整合 | モジュールに乗らない、通り芯からずれる | 照明がグリッドから外れている |

### 7.2 指摘の形

```python
class Issue:
    id: str
    kind: Literal["clash", "clearance", "coverage", "fit", "alignment"]
    severity: Literal["law", "standard", "assumption"]
        # law:        法規の違反（直さなければ建たない）
        # standard:   設計標準からの外れ（設計者の判断で許容できる）
        # assumption: 確度0 の部材だけが関わる（仮定どうし）
    elements: list[str]        # 関わる部材の id
    rule_id: str | None        # 反しているルール（law/ または standards/）
    measure_mm: float | None   # 重なり量・不足量・漏れの面積など
    location: Point3D
    status: Literal["open", "accepted", "resolved", "returned"]
        # accepted: 設計者が許容（理由を必須）
        # returned: 分野（構造・設備）に差し戻し
    history: list[IssueEvent]
```

- `severity="law"` の指摘は、設計者が「許容」できない。解決するか、分野に差し戻すかの二択。
- 指摘の対応履歴は案と一緒に残す。出図のとき未解決の指摘は紙面に出す。

### 7.3 直し方の候補（LLM と計算の分担）

```
指摘 ─→ LLM：直し方の候補を複数考える
         （部材をずらす／向きを変える／梁の間へ／機種を変える）
     ─→ 計算：候補ごとに建物モデルを仮に変えて、調整エンジンで調べ直す
     ─→ 新しい指摘を生まない候補だけを、影響（他に動く部材）と一緒に見せる
     ─→ 設計者が選ぶ → 子案になる
```

候補を採用できるのは設計者だけ。LLM の候補がどれも通らなければ、「計算で確かめた範囲では直せない」と出して分野に差し戻す。

## 8. 法規と設計標準

| | `solver/law/` 法規 | `standards/` 設計標準 |
|---|---|---|
| 中身 | 建築基準法、消防法とその施行令・規則 | システム天井の寸法、照度の目安、梁せいの概算、器具の標準寸法、離隔の社内基準 |
| 根拠 | 条文番号（必須） | 出典（社内標準・学会・メーカー資料）と版 |
| 差し替え | しない（法改正のときだけ） | 会社・案件ごとに差し替えられる |
| 指摘の重さ | law | standard |
| 作り方 | Claude Code は数値を決めない。条文から表の下書きを作り、**設備設計の担当者が確認**して確定 | ユーザー（会社）が提供。なければ一般的な値を「一般値」と明記して入れる |

総合図で新しく必要になる法規（表を作る時点で条文を確認する）：

- 消防法施行令・施行規則：自動火災報知設備（感知器の種別・受け持ち面積・取り付け位置）、スプリンクラー設備（ヘッドの配置）、誘導灯
- 建築基準法施行令：排煙設備（排煙口の位置）、非常用の照明装置

## 9. 他社図面の取り込み（import/）

### 9.1 流れ

```
DXF / IFC を受け取る
  → ファイルの版を記録（ファイル名・受領日・改訂番号・ハッシュ）
  → 対応表を作る（このレイヤ／このブロック → この部材の種類・分野）
       LLM がレイヤ名・ブロック名から候補を出す → 人が確かめて確定
       確定した対応表は相手先（会社）ごとに保存し、次から使い回す
  → 座標合わせ（通り芯の交点2点で合わせる。ずれ量を記録）
  → 部材を作る（確度2。品番があれば3）
  → 同じ場所の確度0の部材を置き換える
  → 調整エンジンで調べ直す
```

### 9.2 改訂が届いたとき

- 前の版との差分（増えた・消えた・動いた部材）を出す。
- 差分に関わる指摘だけを調べ直し、「改訂で解決した」「改訂で新しく出た」を分けて見せる。

### 9.3 IFC

- 取り込みは DXF から始める（国内の実務で多いため）。IFC は M17。
- IFC は部材の種類をファイル自体が持っているので対応表が簡単になる一方、作り手によって属性の入り方が違うので、DXF と同じ「対応表を確かめる」手順を通す。

## 10. 図面

### 10.1 総合図の種類

| 図 | 内容 | 最初の対象 |
|---|---|---|
| 天井伏総合図 | 天井グリッド、照明、感知器、SP、吹出口・吸込口、点検口、スピーカー、梁（破線） | ◎ 基準階から |
| 床総合図 | OA フロア、コンセント、床吹出、家具の仮置き | ○ |
| 壁総合図（展開） | スイッチ、コンセント、消火栓、表示灯 | △ |
| 断面詳細 | 梁・ダクト・天井・床の重なり、天井懐の寸法 | ○ |
| 指摘一覧図 | 指摘の位置に番号、表で内容 | ◎ |

### 10.2 約束

- すべて `drawing/model` の共通の図面モデルから、DXF・PDF・IFC に出す（現行の約束）。
- **注記ブロック**（企画検討用であること、未考慮事項、既定値の計画条件、適用規定と条文）に加えて、総合図では次を必ず載せる。出力器は、これがない図面モデルを受け付けない。
  - 確度の凡例と、確度0の部材の数・割合
  - 取り込んだ図面の一覧（ファイル名・版・受領日）
  - 未解決の指摘の数（重さ別）
- レイヤ規約（`drawing/layers.py`）は、予約済みの `S-`・`M-`・`E-` を使う。確度はレイヤ名の末尾（例 `E-LITE-0`）か線種で表す（M14 で決める）。

## 11. LLM の役割

| 作業 | LLM | 計算側 |
|---|---|---|
| 条件の翻訳（「コアを東に」「照明を1マスずらす」） | 指示を部材・方向・量に翻訳 | 実行し、調べ直す |
| 結果・指摘の説明 | 文章にする | 数値は結果から直接出す。文章中の数値は結果と照合 |
| 直し方の候補 | 考える | 候補ごとに調べ直し、通るものだけ見せる |
| 取り込みの対応表 | 候補を出す | —（人が確定） |
| 法規・設計標準の値 | **扱わない** | 表からのみ |
| 敷地事実の変更 | **拒否される**（コードで） | — |

MCP（M04）と Web チャット（M09）は同じツール定義を使う（現行の約束）。総合図の段で足すツールの例：

- `place_default(scheme, level)`：仮配置を実行
- `check(scheme)`：指摘一覧を出す
- `move_element(scheme, element, dx, dy)`：部材を動かす（子案）
- `propose_fixes(scheme, issue)`：直し方の候補（計算で確かめたものだけ）
- `import_drawing(scheme, file, mapping)`：取り込み（対応表は人が確定したものだけ）
- `explain_issue(scheme, issue)`：説明

## 12. 検証

| 対象 | 方法 |
|---|---|
| 配置エンジン | 手計算ケース（小さな矩形の天井で、置かれる位置と数を先に書く）。性質テスト（範囲の全点が受け持ちに入る、グリッドに乗る、柱と重ならない） |
| 調整エンジン | わざと干渉させた小さな建物モデルで、出るべき指摘が出て、出るべきでない指摘が出ないこと。重なり量を手計算と照合 |
| 取り込み | 記録済みの DXF（`tests/fixtures/`）で、部材の数・種類・位置が期待どおり。座標合わせのずれ量 |
| 図面 | 注記ブロックの必須項目。確度の描き分け。回帰（出力の固定） |
| 法規の表 | 条文番号の記載漏れを検査。値は担当者の確認記録（`docs/decisions/`）と照合 |
| LLM | 直し方の候補を採用したあと、必ず調整エンジンが通っていること（LLM の出力は信用せず、計算で確かめた結果だけを残す） |

## 13. 段取り（マイルストーン案）

M00〜M09 と日影規制は現行の計画どおり。以下を続ける。

| No | 内容 | 前提 | 最初に価値が出る点 |
|---|---|---|---|
| M10 | 建物モデル：部材・確度・分野の型、通り芯・コア・外壁を載せる | M07 | 骨格がデータとして一つにまとまる |
| M11 | 構造の仮定：梁せい・柱寸法を標準から仮置き（確度0）、天井の懐を出す | M10 | 階高の妥当性が見える |
| M12 | 法規・設計標準の表：消防法（感知器・SP）、非常照明、排煙。担当者の確認つき | M10 | — |
| M13 | 配置エンジン：天井割と仮配置（基準階） | M11、M12 | — |
| M14 | 調整エンジン：ぶつかり・離隔・範囲漏れ・納まり、指摘一覧 | M13 | — |
| M15 | 天井伏総合図の出力（確度の描き分け・凡例・指摘図） | M14 | **最初の総合図（仮定入り）** |
| M16 | 取り込み：他社 DXF（対応表・座標合わせ・改訂差分） | M14 | 本物の図面との重ね合わせ |
| M17 | 床・壁・断面詳細 | M15 | 総合図の揃い |
| M18 | IFC の出し入れ | M16 | 他ソフトとの往復 |
| M19 | 直し方の提案（LLM の候補 → 計算で確認） | M14、M09 | 会話で調整 |
| M20 | 複数階・全館（基準階以外、低層部、屋上） | M17 | 建物全体 |

**最初に確かめたいのは M15**（基準階の天井伏総合図・仮定入り）。オフィスは同じ基準階が続くため、1枚でも実務の効果が見える。ここで「確度の描き分けで仮定が仮定と読めるか」を実際の設計者に見てもらい、M16 以降の進め方を決める。

## 14. 決めてほしいこと

| No | 論点 | 推奨 | 理由 |
|---|---|---|---|
| 1 | 決定 0001「総合図そのものは作らない」を改めるか | 改める（確度つきで作る） | 確度で「根拠のない部材が精密に見える」問題を防げる |
| 2 | 確度の段階 | 4段階（仮定・計画・設計・確定） | 企画→設計→製品選定の流れに対応 |
| 3 | 最初の対象 | 基準階の天井伏総合図 | 繰り返しが多く効果が大きい。部材の種類が限られる |
| 4 | 消防法などの表を誰が確認するか | 設備設計の担当者（社内または協力先） | Claude Code は数値を決めない約束のため |
| 5 | 設計標準の出どころ | 会社の標準。なければ一般値と明記 | 差し替えられる形にしておけば後で直せる |
| 6 | 取り込みの最初の相手 | よく組む構造・設備事務所の DXF 1〜2社分 | 対応表を実物で作れる |
| 7 | 指摘の「許容」を誰ができるか | 設計者（法規の指摘は不可） | 法規違反を許容できる仕組みにしない |

## 15. 危険と対策

| 危険 | 対策 |
|---|---|
| 仮定の部材が「設計済み」と誤解される | 確度の描き分けと凡例・割合の注記を出力器で強制 |
| 消防法の表の誤り | 担当者の確認を記録し、確認のない値は使えないようにする |
| 取り込みの対応表の誤り（照明を感知器と取り違える等） | 対応表は人が確定。取り込み後に種類ごとの数を表示し、人が見て確かめる |
| 他社図面の座標ずれ | 通り芯の交点で合わせ、ずれ量を記録・表示。大きければ取り込みを止める |
| 範囲が広がり、どれも中途半端になる | M15 で一度止めて評価する。基準階の天井だけで完成度を上げる |
| LLM の提案が規定を破る | 提案は必ず計算で確かめ、通らないものは見せない |
